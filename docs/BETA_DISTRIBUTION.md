# Раздача бета-версий

Приложение не публикуется в магазинах, но сборки уходят знакомым на
тестирование. Отсюда два правила, которые дороже всего нарушить.

## Смена идентификатора уносит данные тестировщика

Android определяет приложение по `applicationId`. Сборка с новым ID — это
**другое приложение**: она встанет рядом со старой, а не поверх неё, и старая
унесёт свои данные, когда её удалят.

`4 сентября 2026` идентификатор сменился с `com.example.todo_list_app` на
`io.github.sa1jer.rpgtodo`. Все, у кого стояла сборка до этой даты, проходят перенос:

1. В старой сборке: **Профиль → Данные → Экспорт**, сохранить файл.
2. Удалить старую сборку.
3. Поставить новую.
4. В новой сборке: **Профиль → Данные → Импорт**, выбрать тот же файл.

Без первого шага данные не вернуть. Предупреждайте до раздачи, а не после.

То же самое касается macOS и iOS: контейнер приложения адресуется bundle
identifier, поэтому данные после смены ID тоже переносятся экспортом.

**Windows и Linux — исключение.** Там путь к данным не привязан к
идентификатору приложения, поэтому новая сборка находит данные старой сама, без
переноса.

## Где лежат данные

С `4 сентября 2026` боксы Hive живут в каталоге приложения, в подпапке
`storage`:

| Платформа | Путь |
| --- | --- |
| macOS | `~/Library/Containers/<bundle id>/Data/Library/Application Support/<bundle id>/storage` |
| Windows | `%APPDATA%\<app>\storage` |
| Linux | `~/.local/share/<app>/storage` |
| Android, iOS | приватный каталог приложения, подпапка `storage` |

Раньше они писались прямо в `getApplicationDocumentsDirectory()` — на Windows и
Linux это настоящая пользовательская папка «Документы», куда приложение
вываливало тринадцать файлов `.hive` вперемешку с документами человека.

Перенос из старого места в новое происходит сам, при первом запуске, и только
если в новом каталоге ещё пусто. Старые файлы остаются нетронутыми: пока
несколько релизов не подтвердят новое место, они — запасной путь.

Второй раз это произойдёт при переезде на собственный домен (см. ниже), поэтому
менять ID лучше как можно раньше и как можно реже.

## Подпись: ключ теряется — теряются обновления

Android ставит обновление поверх установленного приложения, только если оно
подписано **тем же ключом**. Ключ невосстановим: потеряли — тестировщики
переустанавливают с нуля и снова теряют данные.

Релизная сборка намеренно отказывается собираться без подписи и никогда не
падает обратно на debug-ключ, см. `android/app/build.gradle.kts`.

Ключ создаёт владелец, он же держит пароль.

**Шаг 1. Создать ключ.** Файл кладём в домашний каталог, а не в проект: то, что
лежит вне репозитория, нельзя закоммитить по ошибке.

```bash
keytool -genkeypair -v -keystore ~/rpg-todo-release.jks -storetype PKCS12 -alias rpg-todo -keyalg RSA -keysize 2048 -validity 10000 -dname "CN=RPG To-Do, OU=Development, O=RPG To-Do, L=Unknown, ST=Unknown, C=RU"
```

`-dname` задан заранее, поэтому команда спросит ровно одно — **пароль**, и
попросит повторить его. Ввод не отображается, это нормально.

Пароль **один**. В PKCS12 (формат по умолчанию с JDK 9) у ключа нет отдельного
пароля от пароля хранилища; в `key.properties` одно и то же значение указывается
дважды. Восстановить пароль нечем — сразу в менеджер паролей.

`-storetype PKCS12` указан явно, чтобы на другой машине со старой JDK не
получилось хранилище формата JKS с другой моделью паролей.

`-validity 10000` — около 27 лет. Меньше ставить не стоит: истёкшим ключом
нельзя подписать обновление.

**Шаг 2. Заполнить `android/key.properties`.** Шаблон лежит рядом:

```bash
cp android/key.properties.example android/key.properties
```

Подставить полный путь к `.jks` (не относительный) и пароль в оба поля.

**Шаг 3. Сделать резервную копию** файла `.jks` и пароля туда же, где вы храните
пароли. Не в проект и не в репозиторий.

`android/.gitignore` закрывает `key.properties`, корневой `.gitignore` — любые
`*.jks` и `*.keystore`. Проверить перед первым коммитом после создания ключа:

```bash
git status --porcelain --ignored | grep -E "key\.properties|\.jks"
```

Строки должны быть помечены как игнорируемые. Резервная копия ключа хранится
там же, где вы храните пароли, а не в проекте.

## Номер сборки растёт с каждой раздачей

Android ставит обновление поверх установленного, только если `versionCode`
**строго больше** установленного. Одинаковый номер — установщик молча откажет,
и тестировщик решит, что сломалась сборка.

`versionCode` берётся из числа после `+` в `pubspec.yaml`:

```yaml
version: 1.3.64+2
#               ^ это versionCode
```

Увеличивайте его перед каждой сборкой, которую кому-то отдаёте. Номер до `+`
(`1.3.64`) — это то, что видит человек, его меняйте по смыслу.

Проверить, что попало в собранный APK:

```bash
$ANDROID_HOME/build-tools/37.0.0/aapt2 dump badging build/app/outputs/flutter-apk/app-release.apk | head -1
```

## Как выложить сборку

```bash
tool/release.sh              # поднять номер, собрать, проверить, выложить
tool/release.sh --dry-run    # то же, но без публикации
```

Скрипт делает по порядку: поднимает `versionCode`, синхронизирует ярлык версии
в `lib/utils.dart` с `pubspec.yaml`, собирает релиз, **спрашивает у самого APK**,
чем он подписан (собралось — не значит подписалось нужным ключом), и выкладывает
через `gh release create` с тегом вида `v1.3.64+3`.

Номер сборки в теге — не украшение: приложение читает именно его, чтобы понять,
отстало ли оно. Релиз, выложенный руками без `+N` в теге, приложение сравнить
не сможет и промолчит.

Нужен `gh` и авторизация: `brew install gh && gh auth login`.

## Уведомление об обновлении

Приложение раз за запуск спрашивает у GitHub последний релиз и, если
установленная сборка старше, показывает строку в профиле со ссылкой.

Сознательные ограничения:

- **Только уведомление, без установки.** Скачивание и установка APK изнутри
  требуют разрешения `REQUEST_INSTALL_PACKAGES` — оно чувствительное и
  закрывает дорогу в магазин.
- **Ссылка копируется в буфер**, а не открывается: для открытия браузера нужна
  отдельная зависимость, и её пока нет.
- **Молчание при любой ошибке.** Нет сети, лимит GitHub, чужой формат ответа —
  приложение ничего не показывает. Фоновая проверка не должна мозолить глаза.
- **Черновики и предрелизы игнорируются**, и откат назад не предлагается.

## Идентификатор окончательный

`io.github.sa1jer.rpgtodo` выбран как постоянный ID, включая публикацию.

Обратный DNS предполагает домен, которым владеет издатель. Домена нет, и вместо
покупки взята конвенция GitHub Pages: право на `sa1jer.github.io` подтверждается
самим аккаунтом `Sa1jer`, поэтому префикс `io.github.sa1jer` законно ваш и ни с
кем не столкнётся. Платить за это ничего не нужно.

Менять его больше не нужно и не следует: после публикации ID не меняется вовсе,
а до публикации каждая смена стоит тестировщикам их данных.

Если когда-нибудь появится собственный домен — ID **всё равно остаётся этим**.
Домен пригодится сайту и почте, но переезд идентификатора обойдётся дороже, чем
принесёт.
